# ADR-0020 — 首頁把 bento 與 masonry 上下疊，不並排也不交錯

- **Status:** accepted
- **Date:** 2026-08-11

## Context

首頁要同時回答兩個問題，而這兩題的組織原則互斥：

| | 「我的東西怎麼樣了」 | 「接下來聽什麼」 |
| --- | --- | --- |
| 版型 | **bento** | **masonry** |
| 內容 | 正在播放／今日練習／本週訊號／連續天數／難點詞庫 | 已訂閱 feed 的單集 + 示範集 |
| 數量 | **固定五塊**，可窮舉 | **無界**，一路長下去 |
| 意義從哪來 | **位置與大小**（62:38 的那一排＝待練比連續天數重要） | 卡片同構，只有時間順序 |
| 邊界 | 每一塊都量得完 | 下緣**刻意不齊**＝「還有更多」 |
| 改一塊的成本 | 重新設計整張網格 | 就是多一張卡 |

「大小＝重要性」是 bento 唯一的表達手段；「下緣不齊」是 masonry 唯一的表達手段。
兩者都需要**自己那一整條螢幕寬**才成立。

考慮過三種擺法：

1. **並排**（左 bento、右 masonry 兩欄）——iPhone 寬度下每欄約 170pt。bento 的大塊
   會塌成跟探索卡一樣寬，「大小＝重要性」當場失效；masonry 只剩一欄，參差的下緣也
   沒了，變成一條普通清單。兩邊的表達手段同時歸零。這個擺法要到 iPad 才成立。
2. **交錯**（把 bento 磚當成特殊卡片丟進同一個分欄演算法）——最誘人，因為只要維護
   一份清單。但 `MasonryList` 的 packer 是 shortest-column-first：一塊磚落在哪，取決於
   **排在它前面的所有卡片的高度**。也就是「連續天數」會隨著使用者多訂了一個節目
   而換位置。bento 的意義綁在位置上，位置一浮動意義就沒了。若要在 packer 裡加
   「這幾個 index 釘死」的例外，等於把兩套規則塞進同一個演算法——而那個演算法的
   全部價值就是它只有一條規則。
3. **上下疊** —— 選這個。

## Decision

**上半 bento、下半 masonry，而且整頁只有一個捲動容器。**

`MasonryList` 自己就是那個 `ScrollView`，五個 bento 區塊是它的 `ListHeaderComponent`，
見底的提示是 `ListFooterComponent`。兩者共用同一個 `GAP = SP(3)`，上下看起來才是同一
張網格；但欄的規則各自獨立（bento 的比例由設計決定——例如 `row2` 的 62:38；masonry
的欄寬由 `pack()` 依實測寬度算）。

**bento 不做成固定不捲的上半部。** 它加起來約 650px，任何一支 iPhone 都塞不下它加
兩排卡片，釘住只會把探索壓成一條縫。**「版面固定」指的是區塊數與相對大小不隨資料
變動，不是它不會捲。**

螢幕矮於 `COMPACT_HEIGHT`（700）進 compact：**縮 hero、降 row2 的高，不砍區塊**。
區塊數是 bento 意義的一部分，少一塊等於改了版型；小螢幕的使用者該看到同一張網格的
縮小版，不是另一個首頁。

## Consequences

**變容易的**：一個捲動容器就沒有巢狀捲動——兩個 `ScrollView` 疊在一起時內層吃掉外層
的拖曳，是 RN 上最難調的一類 bug，這裡從結構上不會發生。ADR-0019 留的那條後路
（「捲過 hero 就淡入 mini player」）也已經備好：`onScroll` 從 `MasonryList` 透出來了，
真要做不必改結構。

**變難的 / 被綁住的**：

- **放進 header 的手勢元件必須主動跟外層 `ScrollView` 讓路。** 本輪的 `VolumeSlider`
  就踩過：`onStartShouldSetPanResponder` 回 `true` 會讓從音量條上開始的**垂直**拖曳
  被音量條吃掉，因為 RN 在已有 responder 的情況下**不會**把 `onMoveShouldSetPanResponder`
  派給 responder 自己——寫在那裡的方向判斷是永遠跑不到的死碼。正解是 start 回
  `false`、只在 move 階段依方向搶，代價是失去點一下就設定的能力。這個坑對每一個
  之後想放進 header 的可拖曳元件都成立。
- **header 與清單都不虛擬化。** bento 五塊本來就整塊掛著，`MasonryList` 也沒有虛擬化
  （理由見該檔檔頭）。首頁的總掛載成本 = 五塊 + 已載入的卡片，唯一的節流閥是分頁
  （每次 +10）。長到上百張時該收斂分頁上限，而不是回頭找虛擬化套件——那是原生依賴。
- **bento 每 250ms 跟著播放位置重繪，而它是清單的 header。** 所以每張卡都必須 `memo`、
  傳給卡片的 callback 必須身分恆定（`handlersRef`），否則每秒四次重畫整個清單。
  這是上下疊獨有的隱性成本（並排／交錯沒有，但它們各有更糟的問題）。
- **想在 bento 加第六塊，必須重新設計整張網格**，不能順手塞在後面——一塞就開始往
  masonry 的方向漂移，而漂到一半的版型兩種表達手段都拿不到。會一直長的東西應該進
  masonry，或者變成自己的分頁。
- masonry 只吃「已經有的東西」（示範集 + 已訂閱 feed 的單集），所以見底的 footer 必須
  把人送去探索分頁（ADR-0019）。這個交接是結構的一部分，不是文案。

**沒有 supersede 任何 ADR。** 與 ADR-0019 是同一塊畫面的兩個不同層級：0019 決定外殼
（幾個分頁、mini player 在哪常駐），這份決定首頁**內部**怎麼組織。ADR-0018 的
「每畫面最多一個 `<Gradient>`」在這裡仍然有效——首頁那一個用在 hero，masonry 的卡片
一律不得再開。
