# ADR-0024 — 互動式通知是 Live Activity 的降級替身；它的職責是**啟動器**，不是聽力練習

- **Status:** accepted
- **Date:** 2026-08-14

## Context

ADR-0021 的鎖屏複習卡需要 widget extension，widget extension 是原生 target，**不能 OTA**。
本輪（08-14）到 Pre-Demo Day（8/17）之間沒有再做一次 EAS Build 並讓使用者重裝的空間，
所以改用本地排程 + 通知 category 補位。**那套機制記在 ADR-0022**（出題器沿用、category
identifier、SRS 單向寫入、冪等三層、日期閘）。

**這一份記的是另一件事：那個替身補到哪裡、缺在哪裡，以及它因此被允許長成什麼。**
機制與天花板分開兩份，是因為機制會隨 SDK 與 Expo 的 bug 修復而改，天花板不會——
`opensAppToForeground` 哪天可以安全地設成 false，通知仍然不是聽力練習。

需要獨立紀錄的直接理由是：**ADR-0021 ③ 明文否決過「用通知 action 做互動答題」**，理由是
「使用者按了，但要等他回來才算數——那正好是我們要繞開的東西」。本輪把它做了。

這不是推翻 0021 ③，是**比較對象換了**：0021 ③ 拿通知去比一個做得出來的 Live Activity；
本輪能拿來比的只有「什麼都沒有」。這句話必須寫下來，否則三週後翻 ADR 的人只會看到兩份
自相矛盾的紀錄，然後憑當下的心情挑一份信。

## Decision

### ① 缺口盤點：補到的是「他在鎖屏上被問了一次」，沒補到的是「常駐」與「不進前景」

| 鎖屏複習卡（ADR-0021 要的） | 通知（ADR-0022 本輪做的） | 補到了嗎 |
| --- | --- | --- |
| 鎖屏上**常駐**一張卡，鎖著螢幕就看得到 | **響一次**的事件；划掉或進了通知中心就要自己去翻 | ❌ |
| 題面 + 三選項 + 逃生口**同時可見** | 題面在標題（永遠看得到），選項在**收起來**的 action 裡，要下拉 | 🟡 |
| 答完**就地**換下一題 | 一則一題；答完人已經在 app 裡，下一題是另一則通知 | ❌ |
| 那一按跑純 Swift，**不進前景** | 那一按把 app 帶到前景才處理得了（見 ②） | ❌（刻意） |
| 答案落地是檔案系統層級的不變式（App Group 穩定鍵） | 答案在通知自己的 `data` 裡，靠冷啟動收割 + 三層冪等 | 🟡 |
| 需要 widget extension → **要 build** | 純 JS → **OTA 可送** | ✅（它存在的唯一理由） |

**「七成」是估計，不是量測**，而且本輪連量的機會都沒有（見 Consequences）。它的意思只有
一句：鎖屏複習卡的價值主力來自「一個英文詞在他沒有預期的時候出現，而他必須從記憶裡把它
撈出來」——那一件事通知做得到，所以 ADR-0022 ④ 把**題面直接寫進通知標題**（他不下拉、
不作答，光看到那個詞就已經是一次提取練習）。做不到的是「撈完就地撈下一個」與「撈的時候
不用離開鎖屏」。

### ② 四顆按鈕全部 `opensAppToForeground: true`——這是把「不進前景」那一格**主動放棄**

理由是可靠性，不是偷懶：`opensAppToForeground: false` 的 action 在 app 被殺時**不會**觸發
`NotificationResponseReceived`，官方指定的替代路徑是 `registerTaskAsync` 背景任務，而
expo #36282（至今未解）正是那個窗口的 JS 不保證執行完畢。機制細節見 ADR-0022 ③，這裡
不重述。

**要記的是這個放棄改變了這個功能是什麼。** 按鈕必然把 app 帶到前景 ⇒ 它在物理上就是一個
**啟動器**。設計要順著這件事走，不要假裝它是鎖屏答題：

- `App.tsx` 那側刻意**不暫停播放、不關覆蓋層、不切分頁**（0022 ③）——按鈕已經把 app 帶到
  前景，那本身就夠打擾了。
- 回饋只有一行字、4 秒後自己消失。它**不是一個「答題結果畫面」**，它是「你人已經在 app
  裡了」。要一個答題結果畫面，就等於承認我們以為那一按是一次練習。

### ③ 通知裡沒有**我們的**播放器，所以它只承載不需要聽的題型

先把事實講準，免得下一輪以為我們沒查：**iOS 的通知可以帶音訊附件**
（`UNNotificationAttachment`；`expo-notifications@57` 的
`NotificationContentInput.attachments` 就是它），展開的通知介面會給一顆播放鍵。
我們仍然不用，三個理由，第三個是決定性的：

1. 附件必須是**排程當下就存在的本機檔**。遠端 URL 要 Notification Service Extension——
   又一個原生 target、又一次不能 OTA，正好是我們在躲的東西。
2. 音訊附件有大小上限（Apple 文件列的是 5MB），而且要在**排程時**就決定播哪一句。今天連
   Mirror 音檔都還一個都沒有（ADR-0025）。
3. 🔴 **在通知介面播的音，JS 完全看不到。** 沒有位置取樣、沒有倒帶、沒有 `replay_event`。
   ADR-0002 說我們自己做播放器、ADR-0003 說所有重聽走同一條管線，兩份的理由都是同一句：
   **倒帶才是產品。** 量不到的音訊不是聽力練習，是聲音。

所以通知能出的題只剩「不必聽就能答」的那一類——本輪是**詞義提取**（英文題面 → 三個中文
釋義 + 想不起來）。那是所有題型裡最弱的一種：它測的是詞義取回，不是**聽得出來**。
`captureEngine` 收到的那個訊號從頭到尾是聽覺的，通知這條路碰不到它。

### ④ 因此天花板寫死：通知答題永遠不計入「練了」

- 不寫 `status: 'practiced'`、不 `addPracticeRecord`、不計入 daily session / streak /
  ADR-0011 的北極星。0022 ⑤ 已經是硬規則；**這裡記的是為什麼那條規則不會鬆**——不只是
  「1/3 猜對率會灌水」，而是這條路徑在物理上碰不到聽覺，它連測都沒測到那件事。
- SRS 只准單向寫（答錯／想不起來 → `'again'`），且要過卡片資格閘（0022 ⑤-b）。
- **要替它訂指標的話，指標是轉換率不是答對率**：通知送達 → app 被打開 → 當天完成至少一張
  卡。答對率在這條路上是一個沒有意義的數字（1/3 猜對率 ＋ 只測詞義），拿它上 pitch 會被
  一句「那你怎麼知道他聽得出來」問倒，而那一問是對的。

## Consequences

- 🔴 **這套流程從未在實機上跑過一次。** 排程、category 註冊、下拉、按下按鈕、冷啟動收割、
  回饋那一行字——全部只有 `tsc` 與 `expo export` 過得去。所以上面每一格「補到了嗎」都是
  **推演**，包括「題面永遠看得到」這種看似穩的一格。第一次實機測試該做的是照著這張表
  逐格對，而不是先看答對率。
- **本輪必然排 0 則題目通知**（0022 Consequences：`gloss_zh` / `distractors_zh` 沒有生產者）。
  也就是說本輪真正交付的是「有題就發得出去」的那條路，**不是**「他每天會被叫回來」。
  在生產者做出來之前，這個啟動器連一則都發不出去，**不准在任何地方講成功能已上線**。
- **Live Activity 真的做出來那天，這份不被 supersede**——分工反而更清楚：通知是事件／
  啟動器，Live Activity 是常駐表面（0021 ③ 那張表原封不動成立）。但**兩者同時存在之前
  必須先解一個問題**：0021 的答案落在 App Group 容器的穩定鍵檔案，0022 的冪等是模組層
  記憶體 `seenQuizKeys`，兩套互不知道對方存在。同一張卡在鎖屏卡答一次、又從通知答一次，
  會寫兩筆 `'again'`。列為 follow-up，**不要等到兩邊都上線才想起來**。
- **通知的排程節奏此後由「啟動器」這個定位決定**，不是由題庫大小決定。一天三則的上限
  （0022）不是技術限制，是這個定位的直接後果：啟動器發到第四則就從邀請變成騷擾，而被
  關掉通知權限是不可逆的——那會一併帶走每日提醒。
- **不做遠端推播是這一輪的前提，不是暫時的**：推播要 `app.json` plugin（本輪禁令），而且
  一旦經 push 傳輸，`data.correct_id` 就必須拿掉（0022 follow-up）。本地通知從頭到尾沒有
  離開過裝置，正解帶在身上才安全。

**沒有 supersede 任何 ADR。** ADR-0021 ③ 的分工表仍然成立，本份只記錄「本週只有一欄
存在」以及那件事帶來的定位；ADR-0022 是機制，本份是天花板；ADR-0011 的北極星定義
不受影響——本份正是在替它擋住一個會灌水的入口。
