# Rewind 訊號設計（產品的核心，想清楚這個其他都是工程）

## 1. 訊號語意：rewind ≠ 一定聽不懂
人按返回鍵有四種原因：
1. **聽不懂**（目標訊號）
2. 分心了（走路、通知、恍神）
3. 內容太精彩想再聽一次
4. 誤觸

→ 不能天真地把每次 rewind 都當難點。解法是**分層訊號強度 + 把過濾變成練習本身**。

## 2. 訊號強度分層
| 行為 | 強度 | 判讀 |
| --- | --- | --- |
| 同一段 rewind 2+ 次 | ★★★ | 幾乎確定聽不懂 |
| rewind 後降速播放 | ★★★ | 確定聽不懂（速度/連音問題） |
| rewind 後開字幕/逐字稿 | ★★★ | 確定聽不懂 |
| 單次 rewind，之後正常前進 | ★ | 可能分心，弱訊號 |
| rewind 後 3 秒內又 rewind 回更早 | ★ | 大概是找段落，不是難點 |

MVP 規則：**★★★ 自動進入明日練習；★ 進入「待確認」佇列。**

## 3. 關鍵設計：把雜訊過濾變成複習的第一步
隔天的 daily session 開場就是：
> 「你昨天重聽了這 7 段。點掉那些只是分心的。」
使用者花 10 秒滑掉誤報——這個動作同時是：(a) 雜訊標註（免費的 labeled data），
(b) 對難點的第二次曝光（本身就是複習），(c) 讓使用者感覺 app 懂他。
**不要在聽的當下跳出任何確認框**——打斷聆聽心流是死罪，Snipd 的教訓也是 capture
必須零打斷。

## 4. 擷取窗口演算法
- 使用者在時間點 T 按了 back-15s → 難點大機率落在 `[T-15, T]`
- 對該窗口做句子切分（ASR + 標點），取與重播區間重疊的完整句子
- 若同段重播 2 次：兩次窗口的**交集**通常能鎖定到單一句
- 永遠多存前後各 1 句作為 context（診斷連音/文法需要上下文）
- 音檔本身要留：複習時要能重聽原聲（含 0.7x 慢速），這是跟純文字單字卡的
  根本差異

## 5. 診斷分類（產品的大腦）
聽不懂的原因不同，練習方式就完全不同。LLM 對每個 capture 做分類：

| 原因 | 例子 | 對應練習 |
| --- | --- | --- |
| 生詞/片語 | "cut corners" | SRS 卡 + 造句 |
| 連音/弱讀 | "wanna", "shoulda", linking | 慢速對照 + shadowing |
| 語速 | 整句都懂但跟不上 | 0.7x→1x 階梯重聽 |
| 文法結構 | 倒裝、虛擬語氣 | 結構拆解 + 口頭造句 |
| 口音 | 印度/澳洲腔 | 同口音素材推薦 |
| 背景知識 | 美式文化梗、時事 | 一句話解釋即可，不進 SRS |

診斷結果決定這個 capture 進入哪種練習模板。**這個分類層是護城河的起點**：
用得越久，app 越知道「你」的弱點模式（例如：你的問題 80% 是連音不是單字）。

## 6. 為什麼要自己做播放器（而不是做 Spotify 外掛）
- 掌握播放器 = 掌握 rewind 事件 + 精確播放位置 + 音檔存取權，三者缺一不可
- Spotify/Apple Podcasts 不開放這些 API
- 播放器是成熟的輪子（RSS + 音檔串流），2 週能做出堪用版
- Phase 2 時，同一個 app 在背景掛 rolling buffer，耳機手勢走 iOS remote
  command events——**這就是選原生 iOS app 而不是 web 的原因**
